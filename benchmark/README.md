# 기준선

`baseline.json`은 `./gradlew benchmark`의 결과 파일이다. 형식은 `docs/benchmark.md`를 본다.

## 현재 기준선: WSL2 임시값

- 측정일 2026-10-26, Linux 6.18 WSL2, 32 CPU, Java 25.0.3, 작업 디렉터리 ext4, 전체 조건 23개(+지연 2개).
- **베어메탈 NVMe ext4가 아니다.** WSL2 가상 디스크는 fsync 비용을 과소평가할 수 있다. 그런데도 아래처럼 하한 4개를 못 맞췄다. 원인이 환경인지 코드인지는 기준 환경 장비에서 다시 재 봐야 안다.
- 기준 환경 장비에서 다시 잰 값으로 이 파일을 교체한다(`docs/benchmark.md`의 "기준 환경에서 돌리기").

## 하한 확인 결과 (WSL2)

| 검사 | 하한 | 측정 | 판정 |
|---|---|---|---|
| S1 P1 1프로세스 POWER_LOSS | 10,000 msg/s | 2,999 | FAIL |
| S1 P2 1프로세스 POWER_LOSS | 8,000 msg/s | 4,017 | FAIL |
| S1 P3 1프로세스 POWER_LOSS | 4,000 msg/s | 3,345 | FAIL |
| 4프로세스 ≥ 1프로세스의 70% | | P1 POWER_LOSS 55.4%, 나머지 통과 | FAIL 1건 |
| 100만 건 깊이 ≥ 빈 큐의 70% | | 141~262% | PASS |
| S3 p99 같은 프로세스 | 10 ms | 99 ms | FAIL |
| S3 p99 다른 프로세스 | 260 ms | 666 ms | FAIL |

하한은 조정하지 않았다. 터무니없는 값인지는 기준 환경 재측정 뒤에 판단하고, 조정하면 이 표에 근거를 남긴다(조정은 이번 한 번만).

## 릴리스 전 절차

1. 기준 환경(베어메탈 Linux, 로컬 NVMe ext4)에서 다른 부하 없이 `./gradlew benchmark`를 돌린다.
2. 출력의 `regression` 줄에 FAIL이 있으면, 곧 기준선 대비 처리량이 20% 넘게 줄었거나 지연이 20% 넘게 늘었으면 **릴리스를 막는다.** 정확히 20%는 통과다.
3. `floor`, `scaling`, `depth`, `latency` FAIL도 릴리스를 막는다.
4. 의도한 성능 변경이면 원인을 PR에 적고 새 결과를 `benchmark/baseline.json`으로 커밋한 뒤에만 릴리스한다.
5. 기준선과 다른 환경(WSL2 등)의 결과로는 릴리스를 통과시키지 않는다.
