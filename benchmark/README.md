# 기준선

`baseline.json`은 `./gradlew benchmark`의 결과 파일과 같은 형식이다(형식은 `docs/benchmark.md`). 항목 값은 같은 장비에서 3회 잰 값의 중앙값이다.

## 현재 기준선: ns0270

- 측정일 2026-10-26(P4와 단건은 같은 날 나중에 3회), 베어메탈 ProLiant DL360 Gen9, Rocky Linux 9.8, 24 CPU, 62GB, Java 25.0.3.
- 저장소: HP Smart Array P440ar 위 SATA 7200rpm HDD 6개 RAID 1+0, **xfs**. 컨트롤러 쓰기 캐시가 켜져 있고(배터리 백업 1.8GB, 쓰기 90%) 디스크 자체 캐시는 꺼져 있다. 그래서 fsync는 배터리 백업 캐시에서 확정되고 정전에도 캐시 내용이 남는다. `POWER_LOSS`의 뜻은 지켜지지만, 캐시 없는 HDD에서는 훨씬 느리다.
- **티켓이 요구한 로컬 NVMe ext4가 아니다.** 실제 배포 환경의 저장소가 이와 다르면 절대값이 달라진다. NVMe ext4 장비가 생기면 그 값으로 교체한다.
- 다른 부하가 없는 상태에서 쟀다. `ssacli`로 캐시 상태를 확인했다(ns0270에 설치).

## 하한 확인 결과

3회 모두 통과한 검사: P1 ≥ 10,000, P2 ≥ 8,000, P3 ≥ 4,000 msg/s(1프로세스, 빈 큐, POWER_LOSS), 100만 건 깊이 ≥ 빈 큐의 70%, S3 p99 같은 프로세스 ≤ 10ms, 다른 프로세스 ≤ 260ms.

| 검사 | 하한 | 3회 측정 | 비고 |
|---|---|---|---|
| S1 P1 1프로세스 POWER_LOSS | 10,000 msg/s | 15,814 / 14,920 / 15,600 | 통과 |
| S1 P2 1프로세스 POWER_LOSS | 8,000 msg/s | 9,288 / 9,789 / 9,919 | 통과 |
| S1 P3 1프로세스 POWER_LOSS | 4,000 msg/s | 5,840 / 5,743 / 5,629 | 통과 |
| S1 P3 POWER_LOSS 4프로세스 ÷ 1프로세스 | 70% | 68.8% / 68.8% / 73.0% | **경계. 3회 중 2회 미달** |
| S3 p99 같은 프로세스 | 10 ms | 8.1 / 7.7 / 7.2 | 통과 |
| S3 p99 다른 프로세스 | 260 ms | 38.2 / 37.7 / 37.6 | 통과 |

하한은 조정하지 않았다. 값이 터무니없지 않다. P3 POWER_LOSS의 4프로세스 비율만 하한 근처에서 흔들리므로, 릴리스 전 이 검사가 FAIL이면 바로 막지 말고 같은 환경에서 다시 재서(아래 절차 3) 판단한다.

## 4KB(P4)와 단건 대 묶음

P4(4KB, 청크 400)는 스펙 표에 없던 지점이라 하한 없이 기록만 한다. 1프로세스 빈 큐 POWER_LOSS S1은 10,277 msg/s, 4프로세스는 7,625 msg/s(74%)다. 단건 프로파일(P2S, P3S, P4S와 256B의 P0)은 같은 데이터 크기에서 청크만 1이다. 아래는 ns0270 중앙값(msg/s, 1프로세스, 빈 큐)이다.

## 릴리스 전 절차

1. 기준 환경(ns0270 또는 이를 대체한 NVMe ext4 장비)에서 다른 부하 없이 `./gradlew benchmark`를 돌린다. 장비가 바뀌면 컨트롤러 캐시 상태(`ssacli ctrl all show config detail`의 `Cache Status`)도 기록한다.
2. 출력의 `regression` 줄에 FAIL이 있으면, 곧 기준선 대비 처리량이 20% 넘게 줄었거나 지연이 20% 넘게 늘었으면 **릴리스를 막는다.** 정확히 20%는 통과다.
3. 4프로세스 PROCESS_CRASH 항목(`proc4/PROCESS_CRASH`)은 3회 사이 편차가 16~27%여서 한 번 FAIL이 나도 노이즈일 수 있다. 이 항목이나 P3 POWER_LOSS의 `scaling`만 FAIL이면 같은 환경에서 두 번 더 재고 중앙값으로 판정한다. 그 밖의 항목은 한 번이라도 FAIL이면 막는다.
4. `floor`, `scaling`, `depth`, `latency` FAIL도 같은 규칙으로 릴리스를 막는다.
5. 의도한 성능 변경이면 원인을 PR에 적고 새 결과를 `benchmark/baseline.json`으로 커밋한 뒤에만 릴리스한다.
6. 기준 환경이 아닌 곳(WSL2, Windows, 개발서버 등)의 결과로는 릴리스를 통과시키지 않는다.
