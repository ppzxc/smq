# 기준선

`baseline.json`은 `./gradlew benchmark`의 결과 파일과 같은 형식이다(형식은 `docs/benchmark.md`). 항목 값은 같은 장비에서 6회 잰 값의 중앙값이다.

## 현재 기준선: ns0270

- 측정일 2026-11-05(커밋 `45186cf`, 한 JVM 전용 전환(ADR-0012) 뒤 6회, #159), 베어메탈 ProLiant DL360 Gen9, Rocky Linux 9.8, 24 CPU, 62GB, Java 25.0.5(Amazon Corretto).
- 저장소: HP Smart Array P440ar 위 SATA 7200rpm HDD 6개 RAID 1+0, **xfs**. 컨트롤러 쓰기 캐시가 켜져 있고(배터리 백업 1.8GB, 쓰기 90%) 디스크 자체 캐시는 꺼져 있다. 그래서 fsync는 배터리 백업 캐시에서 확정되고 정전에도 캐시 내용이 남는다. `POWER_LOSS`의 뜻은 지켜지지만, 캐시 없는 HDD에서는 훨씬 느리다.
- **티켓이 요구한 로컬 NVMe ext4가 아니다.** 실제 배포 환경의 저장소가 이와 다르면 절대값이 달라진다. NVMe ext4 장비가 생기면 그 값으로 교체한다.
- 다른 부하가 없는 상태에서 쟀다. 같은 장비의 GitHub Actions 러너는 측정 동안 멈췄다. `ssacli`로 캐시 상태(`Cache Status: OK`, 배터리 OK)를 확인했다.
- 이전 기준선(2026-10-26, ADR-0012 이전의 4프로세스·다른 프로세스 측정 포함)은 커밋 `37e1598`의 `benchmark/README.md`와 `baseline.json`에 있다.

## 하한 확인 결과

6회 중앙값으로 통과한 검사: P1 ≥ 10,000, P3 ≥ 8,000, P7 ≥ 4,000 msg/s(빈 큐, POWER_LOSS), 100만 건 깊이 ≥ 빈 큐의 70%, S3 p99 ≤ 10ms. 기존 기준선(2026-10-26) 대비 20% 넘게 나빠진 항목도 없었다.

깊이 비율의 회차 값은 하네스가 회차마다 3바퀴 재서 낸 바퀴별 비율의 중앙값이다. 하한은 조정하지 않았다. 모든 항목이 하한과 여유 있게 떨어져 있다.

이전 기준선과 비교하면 `PROCESS_CRASH`가 크게 올랐다(S1 빈 큐 P1 36,789 → 50,004, P3 11,099 → 23,154, 단건 P4·P6 약 1,320 → 약 2,920). 그 사이 한 JVM 전용 전환(`locking_mode=EXCLUSIVE`, ADR-0012)과 WAL 크기 기준 되감기(ADR-0010, ADR-0017) 등이 들어갔다. 이번 측정에서 원인을 따로 가르지는 않았다. 줄어든 항목 중 가장 큰 것은 S1 P5 POWER_LOSS(10,521 → 9,114, -13.4%)이고 회귀 기준(20%) 안이다.

## 릴리스 전 절차

1. 기준 환경(ns0270 또는 이를 대체한 NVMe ext4 장비)에서 다른 부하 없이 `./gradlew benchmark`를 돌린다. 비율 검사(`depth`)의 S1 조건 4개는 하네스가 기본 3회 재므로 전체 소요 시간은 단발일 때의 약 1.5~2배다. 장비가 바뀌면 컨트롤러 캐시 상태(`ssacli ctrl all show config detail`의 `Cache Status`)도 기록한다.
2. 출력의 `regression` 줄에 FAIL이 있으면, 곧 기준선 대비 처리량이 20% 넘게 줄었거나 지연이 20% 넘게 늘었으면 **릴리스를 막는다.** 정확히 20%는 통과다.
3. `depth`는 하네스가 3회 재서 바퀴별 비율의 중앙값으로 판정한 결과이므로 수동 재측정과 손 계산은 하지 않는다. FAIL이면 그대로 막는다. 비율이 아닌 항목 중 S3 p99만 한 번 FAIL이 나도 노이즈일 수 있다. 이 항목만 같은 환경에서 두 번 더 재고 중앙값으로 판정한다. 그 밖의 항목은 한 번이라도 FAIL이면 막는다.
4. `floor`, `depth`, `latency` FAIL도 릴리스를 막는다(절차 3의 S3 p99 예외 외에는 재측정 없이).
5. 의도한 성능 변경이면 원인을 PR에 적고 새 결과를 `benchmark/baseline.json`으로 커밋한 뒤에만 릴리스한다.
6. 기준 환경이 아닌 곳(WSL2, Windows, 개발서버 등)의 결과로는 릴리스를 통과시키지 않는다. Windows에는 절대 하한을 두지 않는다. 원인과 근거는 [ADR 0008](../docs/adr/0008-windows-has-no-absolute-throughput-floor.md)에 있다.
