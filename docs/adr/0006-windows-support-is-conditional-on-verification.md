# Windows 지원은 목표로 삼되, 검증을 통과한 뒤에 선언한다

smq는 Windows(로컬 NTFS)를 지원하는 것을 목표로 한다. 하지만 아래 세 가지를 Windows에서 모두 검증하기 전에는 README에 "지원"이라고 쓰지 않고, 그때까지는 "미지원(검증 중)"으로 둔다. 검증할 것은 `./gradlew check` 통과, 여러 프로세스가 같은 DB 파일을 쓸 때의 안전성(WAL 공유 메모리와 파일 잠금), 그리고 성능 하한이다. 지원 범위는 로컬 NTFS로 한정한다. SMB 공유, 네트워크 드라이브, OneDrive 같은 동기화 폴더, ReFS, 그리고 WSL의 `/mnt/c`를 거치는 접근은 지원하지 않는다. 이는 Linux에서 NFS와 SMB를 지원하지 않는 것과 같은 이유다. WAL은 같은 호스트의 공유 메모리를 전제하므로 네트워크 파일시스템에서는 안전하지 않고, 검증할 수 있는 범위를 로컬 NTFS로 좁히는 편이 현실적이다. 성능 하한을 Windows에 그대로 적용할지, 별도 값을 둘지, 설정으로 풀지는 Windows와 Linux의 처리량 격차 원인을 밝힌 뒤에 정한다. 이 ADR에서는 하한 값을 정하지 않는다.

라이브러리 소스에는 POSIX 전용 코드가 없고 저장소는 sqlite-jdbc에 맡기므로 동작 자체는 가능해 보인다. 그러나 Windows 벤치마크는 Linux보다 훨씬 느렸고(1프로세스 빈 큐 POWER_LOSS에서 P3 891 msg/s, ns0270은 5,840 msg/s), 100만 건 깊이 비율은 31~66%로 70% 기준에 모두 못 미쳤다. 원인은 확인하지 못했다. 지금은 CI도 없어서 Windows 동작을 계속 확인할 수단이 없다. 지원은 한 번 선언하면 되돌리기 어려운 약속이라([ADR 0005](0005-default-durability-survives-power-loss.md)와 같은 이유), 검증 전에는 선언하지 않는다.

## Considered Options

- 지금 "Windows 미지원"을 명시하고 닫는다: 약속은 가장 약하지만, 방향을 정한 것과 어긋난다. Windows 사용자에게 줄 근거도 남지 않는다.
- 무보증 지원(동작은 하지만 다중 프로세스 안전성과 성능은 보증하지 않는다): 검증 비용이 들지 않는다. 하지만 다중 프로세스 안전성은 정확성 문제이고, 보증하지 않는 라이브러리를 "지원"이라고 부르면 내구성 큐라는 설명과 맞지 않는다.
- 검증 없이 정식 지원을 선언한다: 가장 빠르지만 격차 원인도 모르고 CI도 없는 상태에서 하는 약속이 된다.
