# 단건 처리량은 준비한 문장을 연결에 붙들어 두어 끌어올린다

SQLite 저장소는 연결 하나에 준비한 문장(`PreparedStatement`)을 SQL 문자열마다 하나씩 붙들어 두고 다시 쓴다(`StatementCachingConnection`). 연산마다 문장을 새로 준비하고 해제하던 비용이 단건 한 바퀴(발행, 꺼내기, 정산) 시간의 큰 몫이었기 때문이다. 내구성 수준, 공개 API, 저장소 SPI는 그대로다. 쓰기 트랜잭션 수와 fsync 수도 그대로고, 줄인 것은 트랜잭션 안팎의 CPU 시간뿐이다.

ns0270(#38의 기준 환경)에서 1프로세스 빈 큐 `POWER_LOSS`의 단건 처리량은 P0 472에서 722(+53%), P2S 473에서 719(+52%), P3S 445에서 632(+42%), P4S 453에서 632(+39%) msg/s로 올랐다(6회 중앙값, 스펙 #57의 합격선인 +20% 초과를 네 조건 모두 넘는다). 한 바퀴 시간은 약 2.16ms에서 약 1.57ms가 됐다(`OpProfile` 드라이버 값).

## 실측으로 확인한 것

- `strace`로 센 단건 한 바퀴의 fsync는 `POWER_LOSS`에서 3.02회, `PROCESS_CRASH`에서 0.02회다. 쓰기 트랜잭션 하나가 fsync 하나라는 뜻이고, 이슈가 가설로 둔 "건당 fsync 세 번"이 맞았다. 이 수는 파일시스템과 무관한 코드 구조의 결과다.
- 그러나 시간은 fsync가 지배하지 않았다. ns0270에서 fsync 한 번은 약 0.29ms(배터리 백업 쓰기 캐시)여서 바퀴당 약 0.88ms, 한 바퀴의 약 44%였다. `pwrite64`(바퀴당 14회)가 약 18%, 나머지 약 38%는 SQLite와 JDBC의 CPU 시간이었다. 따라서 이 환경에서는 fsync를 건드리지 않고도 줄일 시간이 남아 있었다.
- 연산별(발행 / 꺼내기 / 정산)로는 `POWER_LOSS`에서 424 / 1,147 / 532µs, `PROCESS_CRASH`에서 181 / 542 / 199µs였다. 꺼내기가 가장 무거웠다.

## Considered Options

- **준비한 문장 캐시(채택)**: 한 가지 변경으로 세 연산이 모두 줄었다(발행 447→390, 꺼내기 1,171→870, 정산 541→312µs). 연결이 하나이고 `SqliteStorage`의 락이 직렬화하므로 공유해도 안전하다. 연결을 닫을 때 모두 해제한다. 문장은 SQLite가 스키마 변경을 만나면 알아서 다시 준비한다.
- **리스 토큰을 난수로(기각)**: 모든 큐가 공유하는 `meta.lease_seq` 행 갱신이 꺼내기에서 페이지를 하나 더 쓰게 한다. 난수 토큰이면 이 쓰기와 중복 `peek`가 없어진다. 그러나 `LeaseToken`은 "저장소 안에서 재사용하지 않는다"고 약속하고, 난수는 이를 확률적 보증으로 낮춘다. 문장 캐시만으로 합격선을 넘어 약속을 약하게 할 이유가 없다.
- **적응형 `anyReady` 건너뛰기(기각)**: 직전 꺼내기가 비어 있지 않았으면 락 없는 사전 확인을 건너뛴다. 문장 캐시 위에서 추가 이득이 약 4%였다. 기준을 5% 미만으로 정했고 상태가 하나 늘어나므로 넣지 않았다.
- **`readOptions`와 `requireQueue` 합치기(기각)**: 조회 두 번을 한 번으로 줄였지만 측정에서 효과가 없었다(꺼내기 1,170 대 1,141µs).
- **`synchronous` 낮추기, 호출 사이 커밋 미루기(기각)**: 성공을 반환한 발행과 정산이 전원 장애 뒤에도 남는다는 ADR 0005를 깬다. 한 호출 안의 트랜잭션은 원래 하나라 합칠 것도 없다.
- **그룹 커밋, WAL2, `BEGIN CONCURRENT`, F2FS atomic write(채택하지 않음)**: 호출자 한 명이 순차로 단건을 처리하는 조건에서는 커밋 수가 줄지 않아 효과가 없다. 여러 호출자가 동시에 쓰는 환경의 개선은 별도 주제다. 자세한 근거는 `docs/research/sqlite-single-write-throughput.md`.
- **꺼내기와 정산을 합친 새 API(이번 스펙 밖)**: 한 바퀴의 쓰기 트랜잭션을 둘로 줄일 수 있지만 공개 API 추가라서 별도 제안으로 남긴다.

## 조건과 한계

- 문장 캐시는 쓴 문장의 `ResultSet`을 호출자가 닫는다는 전제 위에 있다. 열린 채 두면 읽기 트랜잭션이 남는다. 현재 모든 호출 지점이 `try-with-resources`로 닫는다.
- 측정은 배터리 백업 쓰기 캐시가 있는 환경이다. 캐시 없는 디스크에서는 fsync 비중이 훨씬 커서 향상 폭이 이보다 작다. 이 변경은 fsync를 줄이지 않는다.
- 4프로세스 `PROCESS_CRASH`의 빈 큐 값이 회차마다 크게 흔들려(26k~49k), 100만 건 깊이 검사(≥ 빈 큐의 70%)는 6회 중앙값으로 판정했고 70.6%로 통과했다(여유가 거의 없다). 1m의 절대값(약 25~30k)은 변경 전과 같고, 빈 큐가 빨라지면 같은 1m 값에서도 이 비율은 내려간다. 이 검사가 앞으로 FAIL이 나면 `benchmark/README.md`의 릴리스 절차 3에 따라 재측정으로 판정한다.
