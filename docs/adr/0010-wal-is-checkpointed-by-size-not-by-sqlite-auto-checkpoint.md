# WAL은 SQLite 자동 체크포인트가 아니라 파일 크기를 보고 smq가 되감는다

여러 프로세스가 같은 SQLite 파일을 쉬지 않고 읽고 쓰면 `smq.db-wal`이 정산한 데이터와 무관하게 자란다. `randomBench`가 ERROR가 된 실행에서 WAL이 852MB였고(#102), 같은 매개변수(프로세스 4, `PROCESS_CRASH`, 청크 132, 생산자 [0,0,4,4], 소비자 [2,1,1,3], pullWait 371ms)로 부하 시간만 늘려 재 보니 계속 커졌다.

| 부하 | WAL 최대 크기(수정 전) | WAL 최대 크기(`TRUNCATE` 16MB안, 처음 구현) |
| --- | --- | --- |
| 10초 | 1.24GB | 16.8MB |
| 30초 | 1.73GB | 재지 않음(10초와 60초에서 이미 한도 근처에서 멈췄고, 30초는 수정 전 값만 조사 중에 남겼다) |
| 60초 | 2.54GB | 16.9MB |

원인은 smq였다. SQLite의 자동 체크포인트(1000페이지마다, PASSIVE)는 오래된 읽기 연결이 있는 동안 WAL 앞쪽을 되감지 못한다. 연결 여럿의 읽기가 겹쳐 항상 하나는 열려 있으면 WAL이 끝없이 자란다. 한 JVM 안에서 4개 연결이 쓰기만 하면 WAL이 4MB에서 멈췄지만, 겹치는 읽기 연결 둘을 더하자 4초에 877MB가 됐다(`SqliteStorageTest`의 축소판). 부하가 낮은 다른 시드(프로세스 1~4, 두 내구성 수준)는 수정 전에도 4~5MB에서 멈췄다. 정산량이 많고 읽기가 겹치는 부하에서만 드러난다.

그래서 `wal_autocheckpoint = 0`으로 자동 체크포인트를 끄고, 쓰기 트랜잭션을 커밋한 뒤 smq가 직접 한다. 커밋 8번마다 WAL 파일 크기를 확인하고(파일 크기 조회 한 번), 8MB를 넘으면 `PRAGMA wal_checkpoint(RESTART)`를 건다. 이 체크포인트는 새 쓰기를 막고 읽는 연결이 비기를 기다린 뒤 WAL을 끝까지 DB 파일로 옮기고 다음 쓰기가 WAL 앞부분부터 다시 쓰게 한다. 파일은 줄이지 않는다. 되감지 못하면(BUSY) 8커밋 동안은 다시 시도하지 않고 그 뒤에 다시 한다.

되감은 뒤에도 파일은 8MB 이상이므로 크기만 보면 되감을 필요가 없을 때도 매번 체크포인트를 걸게 된다. 그래서 되감은 직후의 파일 크기를 기억해 두고, 파일이 그보다 더 커졌을 때(되감은 구간을 다 채웠을 때)만 다시 건다. 이 기억값과 `journal_size_limit`은 12MB로 한도(8MB)의 1.5배다.

여러 연결(프로세스)이 같은 파일을 쓰면 한 연결이 되감은 WAL을 다른 연결도 같은 크기로 보고 또 되감는다. 되감은 직후라 옮길 것이 거의 없어도 `RESTART`는 쓰기 lock을 잡고 동기화하므로 비용만 든다. 같은 양을 연결 하나와 넷이 번갈아 쓰는 시험에서 WAL이 되감긴 횟수가 69번 대 190번이었다(되감기를 한 연결이 크기만 보던 때). 되감긴 WAL은 첫 쓰기가 WAL 헤더의 salt(바이트 16~23)를 바꾼다(SQLite 파일 형식). 그래서 한도를 넘었다고 판단하면 헤더의 salt를 읽어, 마지막으로 본 값과 다르면 누군가 되감은 것이므로 그 시점의 파일 크기를 새 기준으로 삼고 이번에는 건너뛴다. 헤더 읽기는 한도를 넘었을 때만 한다. 되감기가 계속 막혀 파일이 12MB를 넘게 자랐다면 되감긴 뒤 다음 쓰기에서 12MB로 줄고, 기억값도 12MB를 넘지 않으므로 이후에도 한도 검사가 살아 있다.

## 처리량 회귀와 후보 측정

처음 구현(`TRUNCATE`, 한도 16MB)은 기준 환경(ns0270, xfs)의 `./gradlew benchmark`에서 12개 항목이 FAIL이었다. 단건 청크 S1 POWER_LOSS가 기준선 719~722 msg/s에서 437~449로(-30~-38%), S2 단건이 2800~3284에서 1684~1769로(-34~-46%), S1 P1 PROCESS_CRASH 일부가 -20~-35%, S3 같은 프로세스 p99가 +30%였다. 수정 전 코드는 같은 항목이 PASS였다. 원인은 `TRUNCATE`가 WAL 파일을 0으로 줄이는 것으로 봤다. 자동 체크포인트는 파일을 줄이지 않고 앞부분부터 다시 쓰므로 쓰기가 이미 있는 블록을 덮어쓰지만, 줄인 파일은 이후 쓰기마다 다시 늘어나고 파일 크기 변경(xfs 메타데이터 커밋)이 매 커밋의 fsync에 실린다. 측정으로 확인했다. 같은 조건에서 자동 체크포인트(대조군)는 기준선 범위이고 `TRUNCATE`만 떨어진다.

후보는 ns0270에서 해당 항목만(`--filter`, 바퀴 1회) 재고, WAL 크기는 #102 매개변수(seed 8052834879925507339, 60초)로 개발 장비에서 쟀다. 처리량 단위는 msg/s이고 기준선은 722 / 719 / 3284 / 2806이다.

읽는 법은 다음과 같다. 두 값은 서로 다른 바퀴의 측정이다.

- 파일을 줄이는 것이 회귀의 원인이다. `RESTART`로 바꾸자 크기만 보는 안도 `TRUNCATE`보다 낫고, `journal_size_limit`을 한도에 가깝게 둘수록(파일이 덜 줄수록) 처리량이 오른다.
- 크기만 보는 `RESTART`는 되감은 뒤에도 파일이 한도 이상이라 8커밋마다 체크포인트를 건다. 이것이 583 msg/s에서 멈추게 하는 비용이었다. 되감은 직후의 크기를 기억하는 안이 이를 없앤다.
- 자동 체크포인트를 켜 둔 채 크기만 막는 안은 처리량은 수정 전과 같지만 WAL이 64MB 목표에 근접하거나 넘었다. 여러 연결의 자동 체크포인트가 체크포인트 락을 쥐어 우리 호출이 BUSY로 실패한다. 자동 체크포인트를 꺼야 WAL이 한도 근처에서 멈춘다.
- 선택한 안은 기준선 대비 S1 P0 -4%, S1 P2S -6%, S2 P0 -5%, S2 P2S -6%로 회귀 임계값(20%)과 거리가 있다. WAL은 12.9MB로 목표(64MB)의 5분의 1이다.
 커밋마다 시도하면 읽는 연결이 계속 있을 때 커밋 하나하나에 50ms가 쌓인다. 대기는 연결의 `busy_timeout`을 한 번에 50ms로 줄여서 하고 끝나면 원래 값으로 돌린다. 이미 커밋한 쓰기의 결과는 바뀌지 않으므로 BUSY는 삼킨다. BUSY가 아닌 오류는 숨기지 않고 `SmqStorageException`으로 던진다. 이미 커밋됐으므로 호출자에게는 효력 불명이고, 기존 정책(재시도하지 않는 비BUSY 오류)과 같다.

### 4프로세스 PROCESS_CRASH(S1 P1, 빈 큐) 대조

기준 환경에서 `--filter`로 S1 P1 proc1 `PROCESS_CRASH`, proc4 `POWER_LOSS`, proc4 `PROCESS_CRASH`만 `--repeat 3`으로 재고, 수정 전 저장소 파일(`42925e0^`의 `TransactionExecutor`와 `SqliteStorage`)을 대조군으로 번갈아 돌렸다(msg/s, 바퀴 1·2·3). `PROCESS_CRASH`는 `synchronous = NORMAL`이라 fsync가 체크포인트에서만 일어나고, 되감는 횟수가 처리량을 정한다.

## 지키는 것

- **단일 연결, 단일 lock(ADR-0007, ADR-0009)**: 체크포인트는 같은 연결에서 같은 lock을 쥔 채 돈다. 연결도 lock도 늘지 않는다.
- **내구성 수준(ADR-0005)**: `synchronous`는 그대로다. 체크포인트는 이미 WAL에 들어간 커밋을 DB 파일로 옮길 뿐이라 `POWER_LOSS`와 `PROCESS_CRASH`의 약속이 달라지지 않는다.
- **꺼내기 `wait`(ADR-0009)**: 체크포인트는 커밋 뒤, 호출이 돌아오기 전에 한다. 그래서 `wait`와 별개로 호출 하나가 최대 50ms(체크포인트의 `busy_timeout`) 더 걸릴 수 있다. 되감기가 계속 BUSY여도 8커밋에 한 번만 시도하므로 평균 비용은 커밋당 약 6ms 이하다. ADR-0009가 이미 밝힌 "마감에 `busy_timeout` 한 번을 더한 최악"보다 작은 값이다.

## Considered Options

- **자동 체크포인트 그대로(기각)**: 위 측정대로 WAL이 끝없이 자란다.
- **자동 체크포인트를 둔 채 `wal_checkpoint(PASSIVE)`를 주기적으로 호출(기각)**: PASSIVE는 읽는 연결을 기다리지 않으므로 같은 이유로 WAL을 되감지 못한다. 호출마다 체크포인트가 일어나므로 크기만 보는 방식보다 비용도 크다.
- **자동 체크포인트를 둔 채 한도를 넘으면 `TRUNCATE`(기각)**: 측정에서 `TRUNCATE`의 절반 이상이 BUSY였다. 여러 연결의 자동 체크포인트가 체크포인트 락을 쥐고 있어 우리 호출이 기다림 없이 실패했을 것으로 본다. 자동 체크포인트를 끄자 실패가 줄고 WAL이 한도 근처에서 멈췄다(프레임 수 한도로 비교한 조사 단계의 값이다). 한도를 6MB까지 낮춰도 WAL이 56~73MB였다(위 표).
- **한도를 넘으면 `TRUNCATE`로 파일을 0으로 줄임(기각)**: 처음 구현. WAL은 작지만 단건 청크 처리량이 30~38% 떨어졌다(위 표).
- **`journal_size_limit`만 사용(기각)**: 이 값은 WAL이 되감긴 뒤에만 파일을 줄인다. 되감기 자체가 안 되는 것이 문제였다. 지금은 되감기를 smq가 하고 이 값은 되감긴 파일의 상한으로만 쓴다.
- **한도를 더 작게(8MB 이하)**: 조사 중 프레임 수로 8MB를 잡은 구현은 확인마다 PASSIVE 체크포인트도 돌려 처리량이 낮았다. 지금은 8MB(파일 크기 기준)이고 파일을 줄이지 않으므로 같은 비용이 없다(위 표). 16MB보다 8MB가 단건 처리량에서 같거나 낫고 WAL이 작다. 한도는 60초 부하 목표(64MB)의 8분의 1이다.
- **되감기를 프로세스마다가 아니라 한 곳에서만(기각)**: 별도 스레드나 프로세스가 필요하고 단일 연결 구조를 깬다.

## 조건과 한계

- 자동 체크포인트를 끄므로 WAL이 한도까지 차는 동안 DB 파일은 그만큼 뒤처진다. 읽기는 WAL을 거쳐 같은 결과를 본다. 다른 도구가 이 파일을 열면 그 연결의 설정(기본 자동 체크포인트)을 따른다.
- 한도(8MB), 파일 상한(12MB), 확인 주기(커밋 8번), 체크포인트 대기(50ms)는 이 하네스 부하의 측정으로 정했다. 크기를 조정할 일이 생기면 `randomBench`의 `walMaxBytes`로 다시 잰다.
- 파일 없는 데이터베이스(메모리 등)는 WAL이 없어 확인을 건너뛴다.
- 되감은 직후 크기와 마지막으로 본 salt는 연결 안의 값이다. 두 연결이 거의 동시에 한도를 넘었다고 판단하면(salt를 읽은 직후 상대가 되감는 경우) 한 번 더 되감을 수 있다. 이때 비용은 체크포인트 한 번이다.
- 단건 청크가 아닌 4프로세스 `PROCESS_CRASH`(S1 P1)는 수정 전 코드에서도 표본마다 28k~64k msg/s로 흔들린다(아래). 이 항목의 scaling과 regression 검사는 이 흔들림 안에 있다.
- 기준 환경(ns0270)의 전체 `./gradlew benchmark` 결과는 아래 "최종 확인"에 적는다.
