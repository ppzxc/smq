# SQLite 저장소는 한 JVM만 열고, 락 파일과 EXCLUSIVE 모드로 강제한다

smq는 한 JVM이 쓰는 로컬 큐다. 여러 프로세스가 같은 SQLite 파일을 공유하는 것은 목표가 아니었는데, 문서와 테스트와 벤치마크가 그것을 지원하는 것처럼 쌓여 있었다(ADR-0004, 0006, 0007, 0009, 0010, 이슈 #4, #59, #96, #119). 이 ADR은 범위를 한 JVM으로 되돌리고, 어기면 기다리지 않고 바로 실패하게 한다.

계기는 #119다. `POWER_LOSS`로 여러 프로세스가 같은 파일을 쓰면 쓰기 락을 얻으려는 연결 일부가 굶고, 호출자가 약 25초 뒤 `SQLITE_BUSY`로 실패했다. 락을 쥐는 시간은 짧은데도 driver의 `busy_timeout`은 폴링으로 기다려 락이 비는 순간을 놓친다. 한 JVM 안에서는 연결 하나를 자바 락 하나로 직렬화하므로(ADR-0007) 이 기아가 생기지 않는다. 문제의 전제가 smq가 약속한 적 없는 사용이었다.

## 결정

- 저장소를 열 때 DB 옆의 전용 락 파일(`<DB 파일명>.lock`)에 `FileChannel.tryLock`으로 OS 배타 락을 잡는다. 이미 누가 쥐고 있으면(다른 프로세스, 같은 JVM의 중복 열기) 기다리지 않고 `StorageLockedException`을 던진다. 메시지에 DB 경로와 락 파일 경로가 있다. 락은 DB 파일이 아니라 별도 파일에 건다. POSIX 락은 같은 프로세스가 그 파일의 다른 핸들을 닫으면 풀리기 때문이다. 락 파일은 닫은 뒤에도 남기며, 존재가 아니라 OS 락으로 판단하므로 프로세스가 죽어도 OS가 락을 푼다.
- 연결에 `PRAGMA locking_mode = EXCLUSIVE`를 건다. 락 파일을 모르는 외부 도구(sqlite3 CLI, DB 뷰어)가 파일을 열어도 smq가 쥔 동안은 읽을 수 없다. WAL로 처음 접근하기 전에 켜면 `-shm` 파일이 생기지 않는다.
- 열기 순서는 락 파일, EXCLUSIVE, 첫 접근(스키마 판정), WAL 전환이다. 닫기 순서는 SQLite 연결을 먼저 닫고 락 파일을 푼다.
- 열 때는 `busy_timeout`을 0으로 두고 BUSY를 재시도하지 않는다. 락 파일을 잡은 뒤의 BUSY는 smq 밖의 도구가 DB를 쥔 것이라 기다려도 풀리지 않는다. 이 경우도 `StorageLockedException`이다. #114가 만든 열기 30초 재시도는 이 결정으로 필요 없어져 제거했다. 열기가 끝난 뒤에 `busy_timeout`을 원래 값(5초)으로 올린다.
- 락 파일을 만들거나 잠그지 못하면(권한, 경로 없음) `SmqStorageException`이다. 인메모리 저장소는 바뀌지 않는다.
- 이 변경으로 `0.1.0-SNAPSHOT`부터 호환이 깨진다. 다중 프로세스로 쓰던 사용자는 둘째 프로세스의 `open`이 `StorageLockedException`으로 실패한다. 릴리스 노트에 적는다.

## 검토한 대안

- **BUSY를 총 시간 한도 안에서 재시도하고 `busy_timeout`을 50ms로 줄임(#119의 시도, 기각)**: BUSY 실패는 사라졌지만 처리량이 떨어졌다. 같은 시드로 `main`과 견준 실측은 n=1씩이라 약하다. 시드 247585에서 `main`은 ERROR였고 변경은 843 msg/s에 p50 92.5초였다. 시드 60059에서 `main`은 p50 2ms, 변경은 p50 15.3초였다. 긴 대기(최대 250ms)를 자바 락을 쥔 채 하면 프로세스가 논다는 가설은 확인하지 못했다. 가설과 무관하게, 지원하지 않는 사용을 위해 이 비용을 치를 이유가 없어졌다.
- **재시도 사이에 자바 락을 놓음(기각)**: ADR-0009가 #119 실측으로 이미 기각했다. 이 ADR이 되돌리지 않는다.
- **공정 락(`ReentrantLock(true)`)**: 프로세스 사이의 기아는 자바 락이 풀 수 없다. 한 JVM 전용이 되면 문제 자체가 없다.
- **락 파일만 사용**: 락 파일을 모르는 외부 도구가 DB를 열어 쓰기를 막거나 읽기로 smq의 쓰기 락과 부딪힐 수 있다.
- **`EXCLUSIVE`만 사용**: 같은 JVM의 중복 열기와 다른 프로세스를 구분해 알려 주는 명확한 예외를 못 준다. 첫 접근에서 BUSY로 보일 뿐이다.
- **DB 파일 자체에 `FileChannel` 락**: 같은 프로세스가 DB 파일의 다른 핸들을 닫을 때(sqlite-jdbc가 연다) POSIX 락이 풀린다.

## 결과와 한계

- **디버깅**: smq가 멈춰 있으면 외부 도구로 열 수 있다. 단 도구를 띄워 둔 채 smq를 시작하면, WAL 연결이 공유 락을 계속 쥐므로 smq가 `StorageLockedException`으로 못 연다. 실행 중에는 스냅샷 API(`VACUUM INTO`)가 안전하다(아직 없다, 후속 이슈). `immutable=1` URI로 여는 읽기는 파일이 바뀌면 결과가 틀리거나 `SQLITE_CORRUPT`가 날 수 있는 비상용이다.
- **Windows**: ADR-0006의 "다중 프로세스 안전성" 검증 조건은 "NTFS에서도 거부된다"로 바뀐다.
- **WSL의 `/mnt/c`, 네트워크 파일시스템**: 지원 범위 밖인 점은 그대로다. 락 파일 락도 이런 곳에서는 믿을 수 없다.
- **이전 다중 프로세스 사용이 남긴 `-shm` 파일**이 있는 DB도 열린다(테스트로 확인).
- **당분간 남기는 코드**: 실행 중 BUSY 재시도, 트랜잭션마다 하는 `user_version` 확인, WAL salt 감지, 꺼내기 `wait`의 BUSY 대기 한정은 다중 프로세스를 전제한 코드다. 동작은 바뀌지 않으므로 이 변경에서는 지우지 않고 후속 이슈에서 걷어 낸다.
- **하네스와 벤치**: `randomBench`는 프로세스 수를 1로 고정한다(시드마다 프로세스 수를 뽑던 축을 뺐고, 이 축은 매개변수의 마지막이라 다른 값은 바뀌지 않는다). 고정 프로파일 벤치는 4프로세스와 다른 프로세스 S3 조건을 뺐고 기준선에서도 해당 항목을 지웠다. 자식 JVM을 띄우는 하네스 코드는 후속 이슈에서 걷어 낸다.

## 이 ADR이 부분 대체하는 결정

- ADR-0004: 여러 프로세스가 같은 파일을 공유한다는 전제와, 그 전제 위의 "옛 프로세스가 트랜잭션마다 버전을 확인해 멈춘다"는 동기. 스키마 자동 업그레이드와 거부 규칙은 그대로다.
- ADR-0006: 다중 프로세스 안전성을 Windows 검증 조건으로 둔 것.
- ADR-0007: 다중 프로세스 처리량 측정(4프로세스 항목).
- ADR-0009: BUSY 재시도(시도 5회 × 5초)와 열기 30초 재시도의 동기. 꺼내기 `wait`의 lock 대기 한정과 `lockWaitFloor`는 그대로다.
- ADR-0010: 연결 여럿이 같은 WAL을 되감는 경우의 salt 감지 동기. 크기를 보고 되감는 결정은 그대로다.
