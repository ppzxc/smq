# 스냅샷은 자바 락을 쥔 채 VACUUM INTO로 만든다

ADR-0012로 smq가 열려 있는 동안은 `locking_mode=EXCLUSIVE` 때문에 외부 SQLite 도구가 DB를 읽을 수 없다. 디버깅과 백업을 위해 실행 중에도 일관된 사본을 만드는 `Smq.snapshot(Path)`를 둔다(#127).

## 결정

- `SqliteStorage.snapshot`은 연결을 소유한 자바 락을 쥔 채 트랜잭션 밖(autocommit)에서 `VACUUM INTO`를 실행한다. `VACUUM`은 트랜잭션 안에서 돌 수 없고, 락을 쥐면 사본이 어느 커밋 시점과 일치함이 보장된다. 그동안 `publish`, `pull`, `settle`, `extend`가 멈춘다. 멈추는 시간은 DB 크기에 비례하며, javadoc에 적는다.
- 대상이 이미 있으면 시작 전에 실패한다. 덮어쓰기 옵션은 없다. 대상이 실행 중인 DB, `-wal`, 락 파일과 같은 파일이면(부모 디렉터리의 실제 경로에 파일명을 붙여 비교하므로 심볼릭 링크 디렉터리도 잡는다) `IllegalArgumentException`이다. 부모 디렉터리가 없으면 만들지 않고 실패한다.
- 대상과 같은 디렉터리에 임시 파일을 만들어 `VACUUM INTO`를 하고, `Files.createLink(target, temp)`로 연결한 뒤 임시 파일을 지운다. 연결 전에 실패하면 임시 파일을 지우고 대상은 만들지 않는다. 성공하면 대상이 완전한 파일이다. 임시 파일은 지우지만 지우지 못해도 실패로 보지 않는다(대상이 이미 있는데 호출이 실패하면 안 된다). `link(2)`는 대상이 있으면 원자적으로 `EEXIST`로 실패하므로 검사와 생성 사이에 다른 프로세스가 대상을 만들어도 덮어쓰지 않는다. 하드 링크를 지원하지 않는 파일시스템에서는 예외로 실패하고 폴백은 없다.
- 디스크 여유 공간은 미리 검사하지 않는다. 필요한 공간은 javadoc에 적는다.
- `VACUUM INTO`는 문장이 실행 중이면 거부하는데, 저장소가 붙들어 두는 준비 문장(`executeUpdate`를 마친 것)이 그렇게 센다. 실행 전에 붙들어 둔 문장을 해제하고, 다음 연산에서 다시 준비한다.
- 인메모리 저장소와 테스트용 저장소는 `UnsupportedOperationException`이다.

## 검토한 대안

- **`ATOMIC_MOVE`로 임시 파일을 옮김(기각)**: `rename(2)`는 대상이 있으면 조용히 덮어쓴다. 덮어쓰지 않는다는 약속을 원자적으로 지킬 수 없다.
- **두 번째 읽기 전용 연결(기각)**: ADR-0012의 `EXCLUSIVE`와 충돌한다. 연결이 락을 놓지 않으므로 둘째 연결은 읽을 수 없다.
- **`VACUUM INTO`를 대상에 바로 실행(기각)**: 도중에 실패하면 불완전한 파일이 대상 이름으로 남고, 대상이 이미 있는지 원자적으로 알 수 없다.

## 결과와 한계

- 큰 DB에서는 스냅샷 동안 큐 전체가 멈춘다. 이번 범위에서는 큰 DB 벤치마크를 하지 않았다.
- 하드 링크가 안 되는 파일시스템(일부 네트워크, FAT 계열)에서는 쓸 수 없다.
- 스냅샷 파일은 WAL이 합쳐진 단일 파일이며 락 파일은 만들지 않는다.
