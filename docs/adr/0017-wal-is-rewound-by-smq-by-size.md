# WAL은 smq가 크기를 보고 되감는다

[ADR 0010](0010-wal-is-checkpointed-by-size-not-by-sqlite-auto-checkpoint.md)을 대체한다.

`PRAGMA wal_autocheckpoint = 0`으로 SQLite 자동 체크포인트를 끄고, smq가 쓰기 트랜잭션을 커밋한 뒤 직접 되감는다.

- 커밋 8번마다 WAL 파일 크기를 본다(파일 크기 조회 한 번).
- 8MB를 넘으면 `PRAGMA wal_checkpoint(RESTART)`를 건다. WAL을 끝까지 DB 파일로 옮기고 다음 쓰기가 WAL 앞부분부터 다시 쓰게 한다. 파일은 줄이지 않는다.
- 되감은 직후의 파일 크기를 기억하고, 파일이 그보다 더 커졌을 때(되감은 구간을 다 채웠을 때)만 다시 건다. 기억하지 않으면 되감은 뒤에도 파일이 8MB 이상이라 8커밋마다 헛되이 건다. 기억하는 값은 `journal_size_limit`(12MB)을 넘지 않게 자른다. 되감기가 막혀 파일이 12MB 넘게 자랐더라도 다음에 되감은 뒤에는 파일이 12MB로 줄기 때문이고, 자르지 않으면 이후 크기 검사가 다시 걸리지 않는다.
- `journal_size_limit`은 12MB다. 되감은 파일은 이 크기까지만 남기고 더 큰 부분은 줄어든다.

WAL이 12MB를 넘는 것은 설계대로다. 되감기 전에도 쓰기가 이어지고 확인은 8커밋마다이므로, 상한은 "한도 + 확인 주기 분량"이다.

## 근거

`PROCESS_CRASH`(`synchronous=NORMAL`)에서는 fsync가 체크포인트에만 실린다. 체크포인트 빈도를 줄인 만큼 처리량을 얻는다. 기본 내구성이 `PROCESS_CRASH`인 지금(ADR-0014) 이 근거가 결정을 정한다.

ADR-0010의 원래 근거는 여러 연결의 겹치는 읽기 때문에 자동 체크포인트가 WAL을 되감지 못해 WAL이 끝없이 자란다는 것이었다. 연결이 하나가 된 지금(ADR-0012) 이 근거는 사라졌다. 그 조사는 ADR-0010에 남아 있다.

## 오류와 lock

- **오류**: BUSY를 따로 다루지 않는다. 커밋 뒤 체크포인트에서 나는 SQL 오류는 BUSY든 아니든 삼키고 경고 로그(`System.Logger`)만 남긴다. 이미 커밋된 연산을 실패로 올리면 호출자가 재시도해 중복이 생기기 때문이다. 연산은 정상 결과를 돌려주고, 재시도 상태는 두지 않으며 다음 정규 확인(커밋 8번 뒤)이 다시 시도한다. 되감지 못했으면(결과 행 첫 열이 0이 아니면) 아무것도 기억하지 않고 다음 확인에 맡긴다.
- **lock**: 체크포인트는 같은 연결에서 같은 lock을 쥔 채 돈다. `RESTART` 한 번은 최대 71ms로 꺼내기의 lock 대기 하한 100ms(ADR-0016)보다 작다(#149, ext4, 1회 측정이며 보장은 아니다). `POWER_LOSS`에서 fsync가 멈칫하면 커밋 구간이 100ms를 넘을 수 있고(ADR-0016의 한계), 느린 장치에서는 체크포인트도 그럴 수 있다.
- 파일 없는 데이터베이스(메모리 등)는 WAL이 없어 확인을 건너뛴다.

## 측정

환경은 WSL2, ext4, 32 CPU, Java 25.0.3이고, 다른 부하가 없을 때 변형을 번갈아 3바퀴 돌렸다. 기준 장비 ns0270에서는 재지 않았다. 원본 표와 원자료는 [#139](https://github.com/ppzxc/smq/issues/139)(단일 연결에서 수동 체크포인트와 자동 체크포인트 측정)와 [#149](https://github.com/ppzxc/smq/issues/149)(간격을 늘린 자동 체크포인트 측정)에 있다.

처리량은 manual 대비 배율이다(S1 3바퀴 중앙값).

| 변형 | `PROCESS_CRASH` 프로파일 | `POWER_LOSS` P3/P5/P7 | WAL 최대(60초) | 출처 |
| --- | --- | --- | --- | --- |
| 기본 auto(1000페이지) | 0.47~0.78 | 0.66~0.91 | 4.2~4.3MB | #139 |
| `auto-2048`(8MB 간격) | 0.77~0.94 | 0.94 | 8.5~8.6MB | #149 |
| `auto-3072`(12MB 간격) | 0.87~1.04 | 0.97~0.98 | 12.6~12.7MB | #149 |
| manual(채택) | 1 | 1 | 9.4~11.6MB | #139, #149 |

`POWER_LOSS` 단건(P0/P2/P4/P6)은 fsync가 병목이라 모든 변형이 65~70 msg/s로 같다. `PROCESS_CRASH`의 manual 절대값은 단건 5,000~8,000 msg/s, 묶음 P1 빈 큐 약 95,000 msg/s다.

## 검토한 대안

- **기본 auto 체크포인트(기각)**: 기본값 `PROCESS_CRASH`에서 manual보다 38~53% 느렸다(#139). 두 방식의 `POWER_LOSS` 단건과 p50·p99 지연은 사실상 같았다.
- **간격을 늘린 auto(기각)**: manual의 실효 간격(8~12MB)에 맞춘 `wal_autocheckpoint`다. `auto-2048`의 P5 `PROCESS_CRASH`는 manual의 0.77배였다. `auto-3072`는 P5가 0.87배였고 WAL이 12.7MB로 manual(11.1MB)보다 컸다. 둘 다 채택 기준(`PROCESS_CRASH` 모든 프로파일 0.9배 이상, WAL이 manual 이하)을 만족하지 못했다(#149).
