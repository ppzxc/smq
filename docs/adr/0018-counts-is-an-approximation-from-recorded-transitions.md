# counts()는 기록된 상태 전환을 따라 센 근사값이다

`Queue.counts()`와 `Storage.counts(queue)`는 시각을 보지 않고, 큐마다 메모리에 둔 준비·리스 중·지연됨 개수를 돌려준다. SQS의 `Approximate*` 개수, BullMQ의 대기열 길이, RabbitMQ의 `messages_ready`/`messages_unacknowledged`와 같은 종류의 값이다. (#163)

- 큐마다 숫자 세 개를 `QueueCounts`(바꿀 수 없는 값) 하나로 두고 `volatile` 참조째 바꾼다. 읽는 쪽은 락 없이 참조 하나를 읽으므로 갱신 도중의 섞인 값을 보지 않는다.
- 쓰기 트랜잭션은 변화량을 모아 두었다가 커밋 직후, 이미 쥔 쓰기 락 안에서 반영한다. 롤백이면 반영하지 않는다. 메모리는 메시지 수가 아니라 큐 수에 비례한다.
- 상태 전환: 발행은 준비 또는 지연됨(+1), 꺼내기는 준비·지연됨에서 리스 중으로, ACK는 리스 중(-1), NACK는 리스 중에서 준비 또는 지연됨으로, reject와 소진 이동은 원천 큐에서 빼고 dead letter 큐의 준비에 더한다.
- 시각은 보지 않는다. 기한이 지난 리스는 다시 꺼내기 전까지 리스 중으로, 지연이 끝난 메시지는 꺼내기 전까지 지연됨으로 센다. 다시 꺼내면 만료된 리스는 리스 중에서 리스 중으로 가서 개수가 그대로이고, 끝난 지연은 지연됨에서 리스 중으로 간다.
- 파일을 열 때는 저장된 상태로 한 번 센다. 리스 토큰이 있으면 리스 중, 없고 꺼낼 시각 값이 있으면 지연됨, 나머지는 준비다. 닫고 다시 열기 전후의 개수가 같다.
- dead letter 이동처럼 두 큐가 함께 바뀌는 연산은 큐별로 따로 바꾼다. 두 큐 사이에 짧은 어긋남이 보일 수 있다.
- 용어집의 세 상태 정의는 그대로이고, `counts()`가 근사값이라는 점만 Javadoc과 README에 적는다.

## 근거

smq는 한 JVM, 한 연결, 쓰기 락 하나다(ADR-0012). 읽기 전용 두 번째 연결이 없어 DB를 읽는 `counts()`는 모두 쓰기 락을 지난다. 리스와 지연은 시간이 지나면 쓰기 없이 끝나므로 시각 기준으로 정확히 세려면 행마다 기한을 봐야 하고, 비용이 큐 깊이에 비례한다. 기준 장비 측정(WSL2, 768B, 중앙값)에서 `counts()` 한 번이 깊이 1만 4.4ms, 10만 38.7ms, 30만 151ms였다. 덮개 인덱스를 더해도 2.8, 28.5, 54.5ms로 여전히 O(깊이)다. 12시간 soak에서 이 호출이 쓰기 락을 점유해 프로듀서가 부하 시간의 약 56%를 락 대기로 썼고, 목표 500 msg/s의 8.5%밖에 내지 못했다(#162).

업계 큐도 이 값을 정확히 세지 않는다. SQS는 `ApproximateNumberOfMessages`, BullMQ는 Redis의 LLEN/ZCARD 같은 상태별 구조 크기, RabbitMQ는 `messages_ready`/`messages_unacknowledged`, NATS는 `num_pending`/`num_ack_pending`을 상태 전환 시점에 갱신한다. 요청 때마다 `COUNT`를 도는 pgmq, Hangfire, JobRunr, Oban은 그것이 가장 무거운 질의라고 알려진 쪽이다.

## 대안

- **시각 기준 정확한 개수 유지**: 덮개 인덱스로도 O(깊이)라 락 점유 문제가 남는다. 메모리에 기한을 두는 변형은 메시지 수에 비례하는 메모리와 별도 구조를 더한다.
- **하네스에서 호출 빈도만 낮춤**: 라이브러리의 `counts()`가 깊은 큐에서 쓰기 락을 오래 잡는 문제는 그대로다. 사용자도 같은 일을 겪는다.

## 한계

- 커밋 자체가 실패해 효력을 알 수 없을 때(커밋 중 SQL 오류)는 메모리 개수가 DB와 어긋날 수 있다. 다시 열면 저장된 상태로 맞춰진다.
- 정확한 개수는 `counts()`로 얻을 수 없다. 테스트는 SQL 집계 헬퍼로 메모리 개수가 저장된 상태와 같은지 맞춰 본다.
