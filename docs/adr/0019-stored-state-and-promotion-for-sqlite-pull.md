# SQLite 꺼내기는 저장된 상태와 승격을 쓴다

SQLite 스키마 버전 2에서 꺼낼 메시지는 시각 조건을 행마다 검사하지 않고 저장된 준비 상태로 고른다(#166, #168). 버전 1에서는 최대 전달 횟수 도달 여부와 살아 있는 리스를 확인하거나, 앞쪽의 리스 중·지연됨 메시지를 건너뛸 때 큐가 깊을수록 많은 행을 읽었다. 상태별 부분 인덱스로 이 탐색을 좁히되, 시각이 지나 준비된 메시지는 원래 id 자리에서 다시 고를 수 있어야 한다.

## 결정

- 저장된 준비는 `lease_deadline`과 `available_at`이 모두 NULL인 행이다. 만료 뒤 아직 다시 꺼내지 않았다면 `lease_token`은 남아 있을 수 있다. 저장된 리스 중은 토큰과 기한이 있고 꺼낼 시각이 없으며, 저장된 지연됨은 토큰과 기한이 없고 꺼낼 시각이 있다. 이는 시각을 고려하는 용어집의 메시지 상태와 구별되는 저장 표현이다.
- 꺼내기 트랜잭션에서 단일 활성 컨슈머 큐에 살아 있는 리스가 있으면 빈 결과를 돌려준다. 그렇지 않으면 대상 선택 전에 그 큐의 만료된 리스 기한과 끝난 지연의 꺼낼 시각을 각각 NULL로 바꿔 **승격**한다. 승격 건수에 상한은 없다. 리스 토큰은 남기므로 다시 꺼내기 전의 늦은 정산과 단일 활성 컨슈머가 아닌 큐에서의 늦은 연장이 유효하다. 연장은 기한을 다시 기록한다.
- 승격 뒤 저장된 준비 행을 id 순서로 고른다. 최대 전달 횟수를 다 쓴 준비 행은 기존 상한을 적용해 dead letter 큐로 옮긴다. 대상 상태 조회와 부분 조회를 포함한 UPDATE는 같은 트랜잭션에서 같은 대상을 고른다. 대기용 읽기는 저장된 준비, 만료된 리스, 끝난 지연 중 하나가 있는지 각각 인덱스로 확인한다.
- `counts()`는 토큰이 남은 만료 리스를 계속 리스 중으로 센다. 지연 승격은 지연됨에서 준비로 개수를 옮긴다(ADR-0018).

기존 전체 인덱스 `message_ready(queue_id, id)`는 큐 삭제와 열 때의 집계를 위해 남긴다. 다음 네 부분 인덱스를 추가한다.

| 인덱스 | 열 | 조건과 용도 |
|---|---|---|
| `message_stored_ready` | `queue_id, id` | 기한과 꺼낼 시각이 NULL; 준비 행 선택 |
| `message_lease_deadline` | `queue_id, lease_deadline` | 기한이 NULL이 아님; 리스 승격과 살아 있는 리스 확인 |
| `message_available_at` | `queue_id, available_at` | 꺼낼 시각이 NULL이 아님; 지연 승격 |
| `message_redelivered_ready` | `queue_id, delivery_count, id` | 저장된 준비이고 전달 횟수가 0보다 큼; 최대 전달 횟수 도달 행 선택 |

마지막 인덱스는 미전달 메시지를 포함하지 않는다. 도달 행은 같은 전달 횟수를 가지므로 전달 횟수와 id 순으로 읽어도 id 순서가 유지되고 임시 정렬을 피한다. 버전 1 파일은 ADR-0015의 열기 트랜잭션에서 이 인덱스들을 만들고 토큰이 있는 행의 남은 `available_at`을 지워 버전 2로 올린다. 큰 파일에서는 인덱스 생성 시간이 열기에 든다. 올린 파일은 옛 라이브러리에서 열 수 없다.

## 근거와 비용

#166의 프로토타입은 WSL2, JDK 25, `PROCESS_CRASH`, 100바이트 메시지로 버전 1과 비교했다. 깊은 조건은 각 1회, 얕은 조건은 5회 중앙값이며 판정용 기준선이 아니다. 적체 20만에서 1건 pull+ack는 최대 전달 횟수 큐가 39 → 11,972건/초, 단일 활성 컨슈머 큐가 59 → 15,839건/초였다. 앞의 리스 중 20만 뒤에 준비 메시지가 있는 조건은 16 → 14,580건/초, 앞의 지연됨 20만 뒤는 18 → 15,202건/초였다. 지연 NACK 10만 건은 139,633 → 107,369건/초였고, 리스 10만 건이 한꺼번에 만료된 뒤 첫 꺼내기는 0.3 → 122.6ms였다. 대량 승격 비용과 인덱스 쓰기 비용을 받아들인다. 프로토타입의 상태 조회와 UPDATE는 모두 인덱스를 썼으므로 id별 갱신으로 나누지 않았다.

구현 후 #168의 동일 장비 ABBAAB 각 3회 측정에서는 ns0270, xfs, Corretto 25.0.5 기준 S1 P0 `PROCESS_CRASH` 중앙값이 1,915.486 → 2,374.455건/초(+23.96%), S1 P3이 23,216.56 → 20,768.60건/초(-10.54%), LEASED_HEAD 빈 큐가 42,134.89 → 38,151.55건/초(-9.45%)였다. 이들은 제한된 조건의 변경 전후 비교다. WSL2에서는 P0의 20% 초과 저하가 재현됐으나 변동이 커 원인은 확정되지 않았다. 전체 고정 벤치 기준선의 재측정은 #177에서 별도로 한다.

## 기각한 대안

- **시각 열 하나로 합치기**: 준비 메시지를 id 순서로 고르려면 준비된 행을 모두 정렬해야 한다.
- **메모리 카운터로 스캔만 건너뛰기**: 마지막 전달을 처리 중인 메시지가 있으면 스캔을 피하지 못한다.
- **승격 때 토큰도 지우기**: 아직 다시 꺼내지 않은 메시지의 늦은 정산이 낡은 연산이 된다.
- **승격 건수에 상한 두기**: 시각으로는 준비인 앞쪽 메시지를 건너뛰어 FIFO를 깨뜨린다.
