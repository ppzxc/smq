# 벤치 하네스

smq v1 성능 목표(스펙 #23의 "성능 목표")를 재고, 기준선과 견주어 회귀를 막는 하네스다. 코드는 같은 모듈의 `benchmark` 소스셋(`src/benchmark/java`)에 있고 배포 jar와 소스 jar에는 들어가지 않는다(`./gradlew check`가 `verifyJarExcludesBenchmark`로 jar 내용을 검사한다). JMH는 쓰지 않는다.

## 동작 방식

부모 JVM(`BenchMain`)이 조건마다 새 SQLite 파일을 만들고 큐를 선언해(100만 건 깊이면 미리 채워) 둔 뒤, 자식 JVM(`ChildMain`)을 프로세스 수만큼 띄운다. 자식들은 같은 파일을 열고, 부모가 정한 같은 시각까지 JIT를 데운 뒤 그 시각부터 같은 길이의 구간을 잰다. 자식은 결과를 JSON 한 줄로 표준 출력에 내고, 부모가 합산한다.

- S1: 발행 배치, 꺼내기, 청크 전체 ACK를 반복한다. 처리량은 모든 자식이 구간 안에 ACK한 메시지 수의 합을 가장 느린 자식의 구간 길이로 나눈 값(msg/s)이다.
- S2: 발행만 반복한다. 처리량 계산은 S1과 같다.
- S3: 프로듀서가 50ms마다 발행 배치(P1은 100건)를 내고, 각 메시지에 발행 직전 시각을 적는다. 컨슈머가 청크를 꺼낸 직후 시각과의 차이를 지연으로 모아 p50/p99(ms, nearest-rank)를 낸다. 같은 프로세스는 한 JVM의 두 스레드, 다른 프로세스는 프로듀서 JVM과 컨슈머 JVM을 따로 띄운다.
- 발행 배치 크기와 청크 크기는 프로파일이 정한다(P0 256B/1, P1 256B/100, P2 2KB/300, P3 6KB/500, P4 4KB/400). P4는 스펙 표에 없던 4KB 지점으로 따로 더했다. 같은 데이터 크기에서 청크만 1인 단건 프로파일도 있다(P2S 2KB/1, P4S 4KB/1, P3S 6KB/1. 256B의 단건은 P0이다).

측정 조건은 스펙 표를 그대로 따른다.

| 시나리오 | 조건 |
|---|---|
| S1 | P1~P4 x 프로세스 {1, 4} x {POWER_LOSS, PROCESS_CRASH}, 빈 큐. P0과 단건 프로파일(P2S, P4S, P3S)은 프로세스 1, 빈 큐. P1은 100만 건 깊이도 같은 조합으로 잰다 |
| S2 | P1~P4와 단건 프로파일(P0, P2S, P4S, P3S), 프로세스 1, 빈 큐 |
| S3 | P1만, 같은 프로세스와 다른 프로세스 (POWER_LOSS) |

## 태스크

- `./gradlew benchmarkSmoke`: 짧은 스모크(조건당 약 1.5초). 다중 JVM, 다른 프로세스 S3, 미리 채운 깊이 경로를 한 번씩 지나가는지만 본다. 임계값은 없고 자식이 실패하지 않으면 통과한다. 수치는 의미가 없다.
- `./gradlew benchmark`: 전체 측정(38개 조건, 조건마다 측정 10초와 예열 3초에 준비 시간이 더해진다. 100만 건 깊이는 준비가 더 걸린다). 비율 검사의 분자와 분모가 되는 S1 조건 20개는 기본 3회 재므로(아래 "반복 측정") 총 소요 시간은 단발일 때의 약 1.5~2배다. 수동으로만 돌린다. 결과를 `build/benchmark/result.json`에 쓰고, `benchmark/baseline.json`이 있으면 기준선과 견준다. FAIL이 하나라도 있으면 비정상 종료한다.

### 모듈 경로 실행

`benchmark`와 `benchmarkSmoke`는 smq jar와 그 런타임 의존성(sqlite-jdbc)을 **모듈 경로**에 올리고, 하네스(`src/benchmark` 출력)만 클래스패스에 둔다. 부모 JVM(`BenchMain`)은 `--module-path`와 `--add-modules io.github.ppzxc.smq`로 뜨고, 자식 JVM(`ChildMain`)은 부모의 `jdk.module.path`와 `java.class.path`를 그대로 물려받아 같은 구성으로 뜬다. 그래서 하네스는 `module-info`가 내보낸 `io.github.ppzxc.smq` 패키지의 공개 API만 쓸 수 있고, exports가 블랙박스 경계를 강제한다. 이전에는 main 출력 디렉터리를 클래스패스에 올려 이 경계가 걸리지 않았다.

두 JVM은 시작할 때 `Smq`가 이름 있는 모듈에서 로드됐는지 검사하고, 아니면 바로 실패한다. 실행하면 표준 오류에 `[module] 부모 JVM: ...`과 JVM마다 `[module] 자식 JVM: ...` 줄이 나온다. 하네스를 IDE 등에서 클래스패스로 직접 돌리면 이 검사에서 실패한다. 순수 로직 단위 테스트(`test` 소스셋)는 클래스패스로 돌고 이 검사를 거치지 않는다. 측정 동작은 바뀌지 않는다.

`benchmark`에는 `-Pbenchmark.args="..."`로 옵션을 더할 수 있다.

| 옵션 | 뜻 |
|---|---|
| `--filter <문자열>` | 키에 이 문자열이 든 조건만 돈다. 예: `--filter S1/P1/proc1` |
| `--storage memory` | 인메모리로 돈다. 코어 오버헤드를 보는 진단값이고 임계값은 적용하지 않는다. 한 JVM에서 도는 조건만 있다 |
| `--repeat <횟수>` | 비율 검사의 S1 조건을 재는 횟수(기본 3). 1이면 단발이다. 스모크와 인메모리에는 적용되지 않는다 |
| `--work-dir <디렉터리>` | SQLite 파일을 만들 곳. 기본은 `build/benchmark/work` |
| `--output <파일>` | 결과 파일 위치 |

### 반복 측정

비율 검사(scaling, depth)는 분자와 분모의 측정 흔들림이 곱해져 단발로는 경계에서 흔들린다. 그래서 하네스가 비율의 분자와 분모가 되는 S1 조건(P1~P4 빈 큐의 프로세스 {1, 4} x 내구성 수준 16개, P1 100만 건 깊이 4개, 합쳐 20개)을 기본 3회 잰다.

- 교차 순서: 첫 바퀴에 전체 계획을 돌고, 이어서 이 20개 조건만 두 바퀴 더 돈다. 같은 조건을 연속으로 재면 그 몇 분의 장비 부하가 모든 표본에 같이 실린다.
- 판정은 바퀴별 비율(같은 바퀴의 분자 / 분모)의 중앙값이다. 하한 70%는 그대로다. 한 바퀴만 하한 아래여도 중앙값이 하한 이상이면 PASS다.
- 반복한 항목의 대표값은 중앙값 하나다. `floor`, `regression` 검사, 결과 JSON의 항목 값, 단건 대 묶음 표가 모두 이 값을 쓴다. 나머지 항목(S2, S3, P0, 단건 프로파일 등)은 한 번만 잰다.

## 기준 환경에서 돌리기

1. 베어메탈 Linux에서, 로컬 NVMe의 ext4 위 체크아웃을 쓴다. 작업 디렉터리가 tmpfs나 네트워크 파일 시스템이면 fsync 비용이 맞지 않으므로 `--work-dir`로 NVMe ext4 경로를 준다. 결과 파일의 `environment.workDirFs`에 파일 시스템 종류가 남는다.
2. 다른 부하가 없는 상태에서 `./gradlew benchmark`를 돌린다. 인메모리 진단값이 필요하면 `./gradlew benchmark -Pbenchmark.args="--storage memory"`를 따로 돌린다(JVM 힙은 100만 건 깊이를 담을 만큼 필요하다).
3. 그런 장비가 없으면 WSL2 ext4에서 재도 된다. 이때 결과 파일의 `environment.caveat`에 "fsync 비용을 과소평가할 수 있다"는 경고가 자동으로 들어간다. 결과를 공유할 때 이 경고를 함께 적는다.
4. 기준선은 같은 장비에서 3회 재서 항목별 중앙값으로 만든다. 4프로세스 PROCESS_CRASH 항목은 회차 편차가 커서 한 번 값으로는 흔들린다. 현재 기준선과 릴리스 전 절차는 `benchmark/README.md`에 있다. 새 기준선을 정할 때는 그 결과를 `benchmark/baseline.json`으로 복사해 커밋한다. 하한이 터무니없으면 그때 한 번만 조정한다. 릴리스 전에는 같은 환경에서 다시 돌려 PASS를 확인한다.

하네스는 Windows에서도 돈다(자식 JVM에 조건을 Base64 인자로 넘긴다). Windows 값은 기록용이고 기준선과 비교하지 않는다([ADR 0008](adr/0008-windows-has-no-absolute-throughput-floor.md)).

## 결과와 기준선 파일 형식

결과 파일과 기준선 파일은 같은 형식이라 결과를 그대로 기준선으로 쓸 수 있다.

```json
{
  "environment": {"os": "Linux 6.x", "cpus": "16", "workDirFs": "ext4", "caveat": "..."},
  "entries": {
    "sqlite/S1/P1/proc1/POWER_LOSS/empty:msgPerSec": 12345.6,
    "sqlite/S3/P1/cross-process/POWER_LOSS/empty:p99Ms": 41.2
  }
}
```

반복 측정한 항목은 항목 값에 중앙값을 두고, 바퀴별 값은 `samples` 필드에 덧붙인다(반복하지 않은 항목은 `samples`에 없다).

```json
  "entries": {"sqlite/S1/P3/proc4/POWER_LOSS/empty:msgPerSec": 4100.0},
  "samples": {"sqlite/S1/P3/proc4/POWER_LOSS/empty:msgPerSec": [3900.0, 4100.0, 4300.0]}
```

`samples`가 없는 파일(이전 결과 파일과 `benchmark/baseline.json`)은 항목마다 표본 하나로 읽는다. 기준선은 6회 중앙값이라 `samples` 없이 그대로 쓴다.

항목 id는 `<저장소>/<시나리오>/<프로파일>/<형태>/<내구성>/<깊이>:<지표>`다. 형태는 `proc1`, `proc4`, `same-process`, `cross-process`, 깊이는 `empty` 또는 `1m`이다. 지표는 `msgPerSec`(높을수록 좋음), `p50Ms`, `p99Ms`(낮을수록 좋음)다.

## 비교 보고

비교기는 SQLite 항목만 검사하고 항목마다 한 줄로 보고한다.

```
PASS  floor S1 P1 proc1 POWER_LOSS >= 10000 msg/s  [12345 msg/s]
FAIL  scaling S1 P2 PROCESS_CRASH proc4 >= 70% of proc1  [중앙값 66.0%, 바퀴별 1회 5200 / 9000 = 57.8%; 2회 6000 / 9100 = 65.9%; 3회 6900 / 9000 = 76.7%]
SKIP  regression sqlite/S2/P1/proc1/POWER_LOSS/empty:msgPerSec  [기준선에 없다]
합계: 통과 20, 실패 1, 건너뜀 1
```

| 검사 | 기준 |
|---|---|
| `floor` | 1프로세스 빈 큐 POWER_LOSS의 S1이 P1 10,000, P2 8,000, P3 4,000 msg/s 이상. P0, P4, 단건 프로파일은 기록만 한다 |
| `scaling` | 4프로세스 S1이 1프로세스 값의 70% 이상(P1~P4, 내구성 수준마다). 바퀴별 비율의 중앙값으로 판정 |
| `depth` | P1의 100만 건 깊이 S1이 같은 조건 빈 큐 값의 70% 이상. 바퀴별 비율의 중앙값으로 판정 |
| `latency` | S3 p99가 같은 프로세스 10ms 이하, 다른 프로세스 260ms 이하 |
| `regression` | 기준선에 있는 항목이 20% 넘게 나빠지면 FAIL(처리량은 줄어듦, 지연은 늘어남). 정확히 20%는 통과 |

측정하지 않았거나 기준선에 없는 항목은 SKIP이고 실패가 아니다. `--filter`로 일부만 돌리면 나머지 검사는 SKIP이 된다. FAIL이 하나라도 있으면 종료 코드가 1이다.

## 단건 대 묶음 표

실행이 끝나면 비교 보고 뒤에 같은 데이터 크기에서 청크 1과 묶음의 처리량을 견주는 표가 나온다(임계값 없음, 보여 주기만 한다). 짝은 256B P0/P1, 2KB P2S/P2, 4KB P4S/P4, 6KB P3S/P3이고, S1 POWER_LOSS, S1 PROCESS_CRASH, S2 POWER_LOSS 세 조건을 본다. 한쪽이 없으면 `-`다.

## 성능 참고: 배치 없이 쓰면 느리다

기본 내구성(`POWER_LOSS`)은 쓰기 트랜잭션마다 fsync를 한다. 그래서 메시지를 하나씩 발행하고 청크 크기 1로 꺼내 ACK하면 처리량이 크게 떨어진다. 아래는 베어메탈 서버(RAID 컨트롤러의 배터리 백업 쓰기 캐시가 있는 HDD, xfs)에서 잰 1프로세스, 빈 큐의 값(msg/s)이다. 발행·꺼내기·ACK를 반복하는 조건이고, "묶음"은 발행 배치와 청크를 같은 크기로 키운 경우다(256B 100건, 2KB 300건, 4KB 400건, 6KB 500건).

| 메시지 크기 | POWER_LOSS 단건 | POWER_LOSS 묶음 | PROCESS_CRASH 단건 | PROCESS_CRASH 묶음 |
|---|---|---|---|---|
| 256B | 722 | 16,612 (23배) | 1,805 | 36,789 (20배) |
| 2KB | 719 | 9,797 (14배) | 1,886 | 11,099 (6배) |
| 4KB | 632 | 10,521 (17배) | 1,322 | 10,535 (8배) |
| 6KB | 632 | 5,583 (9배) | 1,327 | 5,282 (4배) |

`POWER_LOSS`의 단건은 약 630~720 msg/s로, 쓰기 트랜잭션마다 fsync가 한 번씩 있어서 묶음보다 훨씬 낮다. 가능하면 발행을 묶고 청크를 크게 꺼낸다.

절대값은 저장 장치와 캐시에 크게 좌우된다. 쓰기 캐시가 없는 디스크나 가상 디스크에서는 `POWER_LOSS`가 훨씬 느리다(WSL2에서는 256B 단건 29 msg/s, 묶음 2,999 msg/s). 기준선과 측정 환경은 [benchmark/README.md](../benchmark/README.md)를 본다.

## 무작위 블랙박스 테스트 (`randomBench`, `randomBenchSmoke`)

고정 프로파일 벤치는 정해진 조건만 돈다. 무작위 하네스(`...benchmark.random` 패키지, 같은 `benchmark` 소스셋)는 시드 하나에서 무작위 워크로드를 만들어 SQLite 저장소에서 돌리고, 불변식 8개(유실, 유령, 중복 범위, dead letter 이동, 지연, 단일 활성 컨슈머, counts, 청크 안 순서)로 판정한다. 처리량과 지연(p50/p99)은 기록만 하고 판정하지 않는다. 고정 프로파일 벤치와 ns0270 기준선은 이것으로 대체되지 않는다. 프로세스 수(1~4)도 시드에서 뽑는다. 1이면 이 JVM의 스레드 여럿이 돌고, 1보다 크면 프로듀서와 컨슈머(프로세스당 0~4, 전체에서 각각 1 이상)가 자식 JVM에 나뉘어 같은 SQLite 파일에 붙는다. 부모는 미리 채우기, `counts()` 표본, 소진, 판정만 맡고 자식이 쓴 발행·전달 기록(`p<n>-*.jsonl`)을 모아 검사기에 넘긴다. 자식 JVM은 고정 프로파일 벤치와 같은 `ChildJvm`으로 띄우므로 자식도 모듈 경로에서 돈다. 태그의 프로세스 구성요소는 자식마다 0부터 달라지고, 부모의 미리 채우기는 자식 수와 같은 번호를 쓴다. 크래시 주입은 없다. 모듈 경로에서 돌고 공개 API만 쓴다. 하네스는 배포 jar와 sources jar에 들어가지 않는다(`verifyJarExcludesBenchmark`).

- `./gradlew randomBench`: 수동 실행. 마스터 시드(기본 현재 시각, 출력에 찍는다)에서 실행 시드를 뽑아 `--budget`(기본 30m)이 다할 때까지 돈다. 예산은 새 실행을 시작할 수 있는 시간이고 도는 실행은 끝낸다.
- `./gradlew randomBench --seed <n>`: 그 시드 하나만 다시 돈다. 같은 시드는 같은 매개변수(프로세스 수와 프로세스별 스레드 수 포함)와 같은 워크로드(메시지 크기와 내용, 지연, 전달마다의 정산 결정)를 뜻한다. 실제 시계로 돌므로 끼어들기 순서까지 같지는 않다. 부하 구간 길이(`--load`)와 스모크의 한도가 다르면 같은 시드도 다른 워크로드이므로, 재현할 때는 같은 `--load`로 돌린다(`randomBenchSmoke`의 시드는 `randomBench`에서 한도가 달라 같은 워크로드가 아니다).
- 옵션: `--seed`, `--budget`(`30m`, `90s`, `2h`, `PT30M`), `--load`(부하 구간, 기본 `10s`), `--master-seed`.
- `./gradlew randomBenchSmoke`: 고정 시드 6개(`Options.SMOKE_SEEDS`, 다중 프로세스 실행 다수 포함)를 실행당 부하 2초로 돈다(다중 프로세스는 자식 JVM을 띄우는 여유가 더해져 전체 약 45초). 미리 채운 깊이는 2,000, 리스 기한은 1초까지로 줄인다. 위반이 있으면 실패한다. `check`에는 넣지 않았고 CI Linux 잡의 별도 단계로 돈다.

실행 한 번은 미리 채우기, 부하 구간, 소진, 검증 순이다. 소진은 발행을 멈추고 두 큐(대상 큐와 dead letter 큐)를 ACK로 비우며, 상한(30초 + 리스 기한 + 2초)을 넘기면 실패다. 부하 중 프로듀서는 쌓인 메시지가 5만 건(미리 채운 몫 별도) 또는 128MB를 넘으면 쉰다.

매개변수는 시드에서 정해진다(이슈 #86의 표): 메시지 크기 0~64KB(로그 균등), 발행 배치와 청크 크기 1~500, 프로듀서·컨슈머 스레드 각 1~4, 내구성 수준, 미리 채운 깊이(0 또는 1천~10만, 데이터 256MB 추정 상한), 정산 비율(ACK 과반), 처리 시간(0~리스 기한의 1.5배, 길면 연장), 리스 기한 200ms~10s, 발행 지연·NACK 지연(비율 0~30%, 0~2s), 최대 전달 횟수(없음 또는 1~5), 단일 활성 컨슈머 20%, 꺼내기 대기 0~500ms.

산출물은 `build/random-bench/`에 쌓인다.

- `runs-<시각>.jsonl`: 실행마다 JSON 한 줄(시드, 풀어 쓴 매개변수, `msgPerSec`, `mbPerSec`, `p50Ms`, `p99Ms`, 판정, 위반 요약, `workDirFs`, `caveat`). 처리량은 부하 구간에서 ACK된 메시지 수이고, p50/p99는 부하 구간에 발행해 지연 없이 처음 꺼낸 메시지의 발행에서 꺼내기까지 시간이다(표본이 없으면 null).
- 세션 끝에 처리량이 낮은 순과 p99가 높은 순 요약 표를 낸다.
- 첫 위반(또는 소진 상한 초과, 예외)에서 멈추고 비정상 종료(코드 1)한다. 시드, 풀어 쓴 매개변수, 어긴 불변식, 관련 태그와 메시지 id를 출력하고, 실패한 실행의 SQLite 파일과 기록(`published.jsonl`, `deliveries.jsonl`, `counts.jsonl`, `violations.txt`)을 `failures/<seed>/`에 남긴다. 통과한 실행의 파일은 지운다.

시각 규약: 발행과 정산은 호출 직전의 벽시계를, 꺼내기는 호출이 돌아온 직후의 벽시계를 기록한다. 검사기는 지연과 단일 활성 컨슈머 판정에 50ms 허용 오차를 둔다.

## CI

CI Linux 잡은 `check`, 배포 테스트 (a), 임계값 없는 `randomBenchSmoke`를 돈다. `benchmarkSmoke`와 `benchmark`는 CI에 연결하지 않았다.
