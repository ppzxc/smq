# Lauren Tan의 Potato Pyramid로 smq 점검

기준은 작업 트리와 원격 main이 일치한 `96de894e029e1df36de0952661c3658c1f98553a`다. 아래 항목은 사용자 제공 영상 요약과 타임스탬프를 기준으로 대조했다. [영상 페이지](https://www.youtube.com/watch?v=ueA116hO_ho)에서 자막과 슬라이드 원문은 확보하지 못했다. 라이브러리 코드, 테스트, 빌드와 워크플로를 읽고 원격 규칙 및 실행 결과를 조회했다. 로컬 테스트를 새로 실행하지 않았다.

## 1. 신뢰에 투자하는 환경

- **생산성과 품질 [01:49]** — Spotless와 공통 저장소 계약, 재사용 가능한 소비자 검증은 수정자마다 같은 피드백을 준다. 작업 시간, 사람 수정 횟수, 병합 후 회귀율의 기준값은 이 점검에서 확보하지 못했다. 자동화 효과를 주장하기 전 대표 PR에서 이 값을 기록한다.
- **환경 투자 [02:10]** — JDK 25, Gradle wrapper, Linux·Windows CI, 배포 소비자 샘플이 이미 있다. 원격 main은 조회 시 `protected=false`, 적용 브랜치 규칙은 0개였다. 검사를 실행하는 것과 실패 시 병합을 막는 것은 현재 별개다.
- **스스로 검증하는 루프 [02:41]** — 에이전트가 실행할 검사는 이미 충분하다. 실패 시 원래 조건을 복원하고, 성공 시 어떤 계약을 확인했는지 PR에서 바로 읽을 수 있는 증거 형식이 다음 투자다. 근거는 [빌드](../../build.gradle.kts), [Linux](../../.github/workflows/linux.yml), [Windows](../../.github/workflows/windows.yml)다.

## 5. 도입 순서와 바깥 루프

1. **신규 문제부터 차단 [19:53, 20:42].** 의존성과 생성 계약 검사를 먼저 추가한다. OS별 잡을 구별하는 이름을 부여하고 이름 변경과 동시에 릴리스의 조회를 맞춘다. Linux·Windows 각각의 `check`와 소비자 잡을 main의 필수 상태로 적용하고 시험 PR에서 누락·실패 시 차단과 성공 시 허용을 확인한다. Linux smoke는 현재 Linux `check` 잡 안의 별도 단계다.
2. **기존 안티패턴 정리 [19:53, 20:42].** 새 검사에 걸리는 부분을 수정하고 `Storage.pull(..., wait)`의 묵시적 기본값을 걷는다. 메모리 락 경합과 SQLite 대기, 인터럽트, 빈 결과 뒤 변경 없음, 유효한 DLQ 플래그 조합을 검증한다. 기존 예외 근거와 문서도 계약에 맞춘다.
3. **검증 강화 [20:04].** smoke 모드와 같은 프로파일 재실행부터 열고 최초 실패 증거를 보존한다. 두 저장소의 가상 시계 기반 명령열 대조와 반례 축소, 장벽을 이용한 두 호출 경합, 표적 변이 검출을 순서대로 추가한다. 계약 위반을 찾으면 재현 사례를 결정론적 회귀 검사로 승격한다.
4. **그 위에서 자동화 [20:08, 20:11, 20:54, 21:16].** 현재 작업은 PR·push CI와 수동 릴리스 중심이다. 피드백·이슈·Slack·알림·신규 릴리스에서 에이전트가 시작해 퍼징·수정 PR·자동 병합·Slack 보고까지 수행하는 흐름은 확인되지 않았다. 먼저 검증 자동 실행과 결과 수집을 대표 변경 한 종류에서 확인하고, 다음으로 수정 PR 생성 여부를 판단한다. 자동 병합과 외부 보고는 필수 검증과 운영자 승인 범위가 확인된 후 검토한다.

해당 SHA의 [Linux](https://github.com/ppzxc/smq/actions/runs/45334549978), [Windows](https://github.com/ppzxc/smq/actions/runs/45334550045), [CodeQL](https://github.com/ppzxc/smq/actions/runs/45334550005)은 성공했다. [릴리스 워크플로](../../.github/workflows/release.yml)는 main push의 두 OS 작업을 검사하므로 릴리스 차단과 PR 병합 차단은 각각 검증해야 한다.

## 6. 당장 적용할 운영 원칙

- **같은 교정이 반복되면 [22:14]** AGENTS.md에 규칙을 추가하기 전에 컴파일 검사, 값 생성 검증, 공통 저장소 계약 중 어디서 막을지 확인한다.
- **신규 유입 차단 뒤 기존 정리 [22:22]** 위 첫 두 단계를 순서대로 적용한다.
- **직접 실행하고 증거를 리뷰 [22:25]** PR에 API 동작, 불변식, 실행 결과와 재현 명령을 연결한다. smq의 우선 산출물은 스크린샷보다 테스트 출력, 상태 전이, SQLite 증거다.
- **위에서부터 한 칸씩 [22:34]** 주석 수와 자동 병합률 대신 규칙이 실제 위반을 막는지, 실패가 같은 조건에서 재생되는지부터 확인한다.

### 확인한 실행의 범위

Windows의 check 로그는 발견 988개, 건너뜀 2개, 실패·오류 0개를 보고한다. 양 OS의 독립 소비자 잡과 Linux의 smoke 단계는 성공했다. 대표 사례 [PR #185](https://github.com/ppzxc/smq/pull/185)는 검사에 통과했고 GitHub 제출 리뷰는 0건이었다. 한 사례만으로 전체 리뷰 관행을 판단할 수 없다. 기준 호스트 성능 벤치, 긴 무작위 검증과 실제 스테이징·공개는 런북의 별도 증거이며, 이 CI 결과로 확인되지 않는다.
